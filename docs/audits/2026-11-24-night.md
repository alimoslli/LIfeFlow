## Findings

### 1. A posted transaction drops what the person did to its pending version (Medium, fix now: wrong numbers)
`plaid.ts:549-606`. A posted row arrives with its own `transaction_id`, so the lookup by `providerTransactionId` finds nothing and a new row is inserted from the bank's values; the pending row is then deleted (`:598-600`). Everything the person set on the pending row is lost: category (when no rule matches), `notes`, and `excluded`.
Scenario: a $42 pending charge is excluded or recategorized in the app (or noted "split with Sam"). Two days later it posts; the new row has no note, the old category, and `excluded=false`, so the $42 returns to spent and the month's total. The existing test (`tests/integration/plaid.test.ts:231`) covers only a kept category on the same id, not pending to posted.
Fix: when `pending_transaction_id` matches an existing row, carry `categoryId`, `notes`, `excluded` and the merchant name to the posted row (or update that row in place to the new id).

### 2. Webhook: forged signatures make us call Plaid each time, with no limit (Low, fix now)
`plaid.ts:797-806`, `webhook/route.ts:20-24`. The route is public and has no rate limit. Only a successful key lookup is cached, so a request with a fresh random `kid` in an unsigned JWT makes one outbound `/webhook_verification_key/get` call carrying our client id and secret. A loop can use up our Plaid request allowance and function time, which can slow real webhooks and Sync now. Related: a cached key is trusted for 24 hours with no refetch when a signature fails, so a Plaid key rotation would reject real webhooks for up to a day (cron still syncs them, so it is delayed data only).
Fix: per-IP limit (`clientIp()`) counted before the key lookup, cache failures for a short time, and refetch the key once when a cached key fails verification.
