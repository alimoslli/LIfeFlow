## Findings (ranked). No high findings.

### 1. Medium, fix now: one account can send unlimited verification texts to any number
`startPhoneLink` (services/sms.ts:38-59) is reached from `startPhoneLinkAction` (settings/text/actions.ts:10-19). Only Pro is checked; `mutate` has no rate limit (nothing in `server/actions.ts`), and the service has none either. Proof: 26 calls back to back with the same number made 26 outbound sends through the fake Twilio. Scenario: a Pro person (or anyone with a paid month) types a stranger's number and taps Send code in a loop: the stranger is spammed with "Your LifeFlow code is ..." texts and LifeFlow pays for every one (SMS pumping, also toll fraud with premium-rate numbers because any `+country` number is accepted). The same path also tells the typer whether a number is "linked to another account" (services/sms.ts:44), which confirms who uses LifeFlow.
Fix: per-account and per-number limits (for example 3 an hour and 10 a day per account, 3 an hour per number) with the email-confirm pattern (`rateLimit`, keyed by user and by number hash), plus an allow-list of countries the Twilio account can text.

### 2. Medium, fix now: the 5-try limit on the phone code can be beaten with parallel requests
`verifyPhoneLink` (services/sms.ts:55-78) reads `attempts`, compares, then writes `attempts + 1` in a separate update (`setSms`, a read-modify-write of the whole `preferences` JSON). Proof: 40 simultaneous wrong guesses were all checked ("That code doesn't match") and the stored counter ended at 1. With a 6-digit code, one burst of a few hundred requests per code and a fresh code per burst (finding 1 gives unlimited fresh codes) gives a real chance to link a number the person doesn't own, which then receives that account's text replies. Also: the same read-modify-write can overwrite concurrent preference changes (a race on `preferences` from the text page and settings), and the code is stored as an unsalted SHA-256 of 6 digits (anyone reading the row recovers it at once; email-confirm uses a keyed HMAC).
Also minor in the same function: `verifyPhoneLink` does not re-check that the number is still free; if two accounts both started linking one number, the second verify hits the unique constraint (`users.sms_phone`) and the person gets a generic error instead of "linked to another account".
Fix: one atomic statement that counts the try and checks the code (like `confirmEmailCode`), a per-account daily try cap that a new code doesn't reset, keyed hash for the code, and a friendly message on the unique violation.

### 3. Medium, fix now: a failed allowance check can show internal error text in the Inbox
`extract.ts:111-119` turns only `AiRefusedError` into a plain message; any other failure of `reserveAi` (a database fault in `ai_reserve`) is rethrown, and `inbox/index.ts:614` stores `e.message.slice(0, 300)` as the item's `reason`, which `inbox/filed-section.tsx:155` and `inbox/upload.tsx:33` show to the person. The same line already shows raw provider errors from `responses.create`. By code reading (not reproduced against a failing database): a pool error or provider 401 text lands on screen. `tidy.ts:46-54` handles the same failure properly (wraps it as `AiUnavailableError`). Fix: map every non-refusal failure to one fixed plain sentence ("Saved, but not read yet. Try again soon.") and keep the raw name only in `recordError`. Note `AiUnavailableError`'s own text, "The allowance check isn't available right now", would also read oddly to a person; it is internal wording.

### 4. Low, fix now: free-message counter is spent before the allowance check and on retries
`api/jarvis/chat/route.ts:43-44` counts the free person's daily message (`jarvis:free:<id>`, 15 a day) before `peekAi` (line 45 on) and before the resend check (line 47). A send refused by an allowance, or a client retry of an already received send (`clientMessageId`), still burns one of the 15. Scenario: a free person at 14 messages, on bad signal, retries one send and is told "You've used today's 15 free messages" with only 14 answered. Fix: count after the checks and skip it for a resend. (Also: "free messages" for a plan with "no free term" is an owner question, see 8.)

### 5. Low, fix now: `cron/notify` does more per person each run and its housekeeping runs last
`api/cron/notify/route.ts:55-60` now runs two extra transactions for every person every 10 minutes (`purgeExpiredVoiceSessions`, `expireStaleAiUsage`), one after another, before the notification work; the housekeeping (`sweepBudgets` line 74, `purgeOldBudgets`, `purgeOldSmsInbound`, `purgeExpiredConfirmCodes`, `purgeOldRateLimits`) only runs if the whole loop finishes inside `maxDuration` 300. Same shape as the 2026-11-08 finding on `cron/promises`. When the loop gets slow, unsettled holds are never swept, so people stay "held" up to their limit (`ai_holds` that nobody settled count against the allowance). Fix: run the housekeeping first (or in its own cron), and select only people who have stale usage or voice rows.

### 6. Low, fix now: CLAUDE.md migration list is out of date
CLAUDE.md "The migrations after 0045" stops at 0063 and says nothing of `0064_email_verified` (1798300000000), `0066_ai_usage` (1798500000000) or `0067_ai_budgets` (1798600000000); the journal on main is in order with no duplicates and no `when` collision (checked). The next number is 0068 with a `when` after 1798600000000.

### 7. Low, fix now: CI notes
`.github/workflows/check.yml:11`: `cancel-in-progress: true` groups by ref, so two quick pushes to main cancel the first commit's check and desktop run, and that commit never gets a result. Use `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. Actions are pinned by tag (`checkout@v4`, `setup-node@v4`, `upload-artifact@v4`), not by commit; fine for a start, worth pinning before launch. The desktop job runs only the desktop project; phone specs (the iphone and mobile projects, including no-overlap-phone, 5 minutes) are not in CI, so a phone-only regression is still caught only by a local run.

### 8. Needs owner: claims and wording

CLAUDE.md allows per-person learned models trained on that person's own data (ADR 0023). It is probably meant as "never trains a shared or the provider's model", but the sentence as written is broader. The owner should pick the exact wording (legal text).
